# ADR-0005：只有 `couple` 做战术改造，其余四个上下文停在战略分层

- 状态：**部分被 ADR-0008 推翻**（2026-10-05）。第 1、2 条仍然有效（Phase A 全项目分层、Phase B 先做 couple，两者都已完成）；第 3、4 条作废——四个支撑域现在一律做到战术改造完成，理由与判据见 `docs/adr/0008-tactical-refactor-covers-all-contexts.md`。本文件保留是为了留下"当初为什么决定不做"的判断依据。
- 相关：`docs/ddd/03-phase-plan.md` 第二节（改造状态表）

## 背景

「把整个项目改成 DDD」有两种诚实度截然不同的做法：把 147 个文件全部铺成四层并各自造聚合（看起来完整，实际四个支撑域没人验证过聚合边界是否划对，是半吊子）；或者承认只有核心域值得立刻投战术成本。

实测支持后者：147 个文件里 couple 占 74，且差异化价值（心动值、双签归属闸门、按天 stableHash 裁决）全在 couple；`filestorage` 4 个文件、`platform` 9 个、`identity` 15 个，业务规则薄且稳定。

## 决策

1. **Phase A 全项目做**：五个上下文一律拿到 api/application/infrastructure 的分层与目录边界（纯移动，行为不变）。
2. **Phase B 只做 couple**：PO 让名（ADR-0002）、聚合与端口、`IntimacyCalculator` 等领域策略对象。
3. 其余四个上下文的 `domain` 包**先不建**，不是建了空包当样子货；它们的既存跨上下文直连由 ADR-0004 的 allowlist 逐条记账。
4. 后续哪一天要动 `messaging` 或 `identity`，按其当期需求再走 B 的同一套规则——那时划聚合边界才有真实的领域专家输入（需求单），而不是现在凭空猜。

## 后果

- 正面：交付的每一步都可验证（编译 + 158 用例），不存在"目录改了但领域是假的"这种债；状态表把未完成部分摆在明面上。
- 负面：项目会在一段时间内呈现「一个上下文完整 DDD、四个上下文只有分层」的不整齐状态——这是**有意的**，状态表与 allowlist 就是为了让这种不整齐可被度量、只减不增。
- 判据：任何人看到 `messaging` 没有 `domain` 包时，能在 `03-phase-plan.md` 第二节查到「未改造」而不是「漏了」。
