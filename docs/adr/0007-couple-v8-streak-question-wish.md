# ADR-0007：v8 第一批（邀请补口 / 每日一问 / 愿望清单 / 连续打卡解锁）的取舍

- 状态：已采纳（2026-10-05）
- 相关：`CONTEXT.md` 统一语言、`docs/adr/0005-only-couple-gets-tactical-refactor.md`、`docs/couple-trim-ranking.md`
- 用户指令：本轮需求由用户一次性给出四条功能与七档解锁清单，并明确「请你决策改动方向，不要让我再参与确认」，
  因此下面每一条自定的取舍都写清依据与代价，供事后复核，而不是留成口头决定。

## 背景

用户提的四条需求里有两条**正好是 2026-10-04 系统裁剪时被删掉的东西**：
`couple_answer`（每日一问互评）与 `couple_checkin`（早安/晚安各自打卡）都倒在 V50/V51 下，
`CoupleQuestions` 静态题库、`src/utils/coupleTheme.ts`（按天轮换主题）也一并删除。
同时「向好友发起邀请、对方同意建立情侣空间」这条需求**其实早就在线**：
`couple_invite` 在 V51 的保留清单里，`CoupleService.invite/accept/reject/cancel` 四个方法与
`CoupleSetup.vue` 的邀请、待处理、撤回三块界面都还在。

所以本轮真正要回答的问题不是"做不做"，而是：**重建时是否照抄旧设计**。
旧设计里有几处是被裁掉的根因（口径含糊、外观与真实进度脱钩、奖励会被没收），照抄就是把它们再养一遍。

## 决策

### 1. 邀请流程不重造，只补领域层与入口

- `couple_invite` 状态机（PENDING/ACCEPTED/REJECTED/CANCELED）与四个端点原样保留，HTTP 契约一字未改。
- 补的一处领域漂移：`CoupleSpace.open()` 建空间工厂此前**零调用方**，`accept()` 走的是
  `CoupleSpacePO.of + spaceMapper.insert` 直插，于是「双方按用户名字典序小者为 userA」这条不变式
  在 PO 与聚合里各写了一遍。现在 `accept()` 经 `CoupleSpaceRepository.save(CoupleSpace.open(...))` 建行，
  规范化只留在聚合一处（`CoupleInviteAcceptTest` 断言 PO 直插不再发生）。
- 补的一处可见入口：通讯录好友的操作菜单里加「邀请建立情侣空间」（`contact-invite-item`），
  此前只有进情侣空间页才能发起，用户视角是"找不到人邀请"。

### 2. 打卡口径只有一条：双方当天都发过贴贴

新立「互动日」这个概念会让 `bondDays`（心动值）与打卡日的口径分叉——同一片数据两个名字，
正是 CONTEXT.md 要避免的事。所以打卡日 = 现有 `bondBothDays` 的"双方当天都发过"这条既有定义，
写入挂钩只有 `CoupleBondService.sendAction()` 一处。

代价（明示，不静默）：只在私聊里说话、没点贴贴的那天**不算打卡**。用户原话是"连续 N 天互动"，
把聊天消息纳入是另一种解读，但那需要 `messaging` 反向调用 `couple`（违反 ADR-0003 的依赖方向），
或由 couple 声明端口让 messaging 实现——为了一个"每天点一下贴贴就够了"的功能不值得动跨上下文契约。
文案上把这条口径写在卡上（「双方当天都贴过才算一天」），不让用户猜。

### 3. 解锁判历史最长，且单调不回退

七档（3/7/14/21/30/50/100）一律按 `BondStreak.longestStreak()` 判定，不按"当前连续"：
断签后已经拿到的气泡、背景、称号**不会被没收**。理由：外观奖励被收回比没拿到更伤人，
而本产品红线是"情绪价值优先"。

配套：解锁推送只在峰值真的跨过档位时发（`tiersCrossed(prevLongest, newLongest)`），
断签后重新爬到同一个数字不会再庆祝一遍。

### 4. 不建 `couple_unlock` / 不建 streak 缓存表

连续天数、解锁档位、`unlockedDay` 全部从 `couple_bond_day` 的 day 集合读时算——
与心动值"读时算无表"是同一手法。曾经考虑过两张表（`couple_streak_state` 缓存 current/longest、
`couple_unlock` 记解锁时刻），否掉的依据：缓存列一旦与真源漂移就成了第二个事实，
而"首次跨过第 N 天的日期"在 day 集合上是可精确派生的（某个够长连续段的第 N 天，取各段最早者）。

一个空间最多几百行打卡日，单次索引查询内存算，代价可忽略。

### 5. 「30 天恋爱等级称号」复用心动值七级称号，不造第二套

用户举例的称号是「初识」「热恋」「默契搭档」，而 `IntimacyCalculator` 已经有七级称号
（怦然心动/心动初启/甜甜热恋/形影不离/心有灵犀/相依相伴/相守一生，阈值 0/50/150/300/500/800/1300），
空间头部本来就在显示它。再造一套按天数走的称号，就是同一个概念两个名字，
而且两套等级会在头部互相打架。

决策：**30 天档只控制"挂到顶部"这个动作**，称号内容取 `IntimacyVO.title`。
未解锁时那一格回到「心动值」，解锁后称号成独立徽章、该格仍写「心动值」，同一个词不出现两次。

### 6. 50 天「定制 emoji」不用双方照片

用户的括号原话是"比如用双方照片生成的贴纸"，这与长期产品红线**直接冲突**
（`AGENTS.md`/`CONTEXT.md`：不做照片/视频上传类功能，服务器部署要求高），
而且裁剪后 `filestorage` 只留 4 个文件，为贴纸重新拉起图片生成链不值当。

替代实现：专属贴纸包由**纯 unicode 组合**构成，内容按双方昵称首字、在一起天数、`space.theme` 确定性派生
（同一对情侣永远拿到同一组，换人不换款），只在 `custom-emoji` 解锁后出现在表情面板。
不新增表、不新增列、不上传任何字节。

### 7. 100 天彩蛋页的「AI 一句话总结」用规则生成，不引入 LLM

实测依据：`pom.xml` 里没有任何 AI 依赖（grep `spring-ai|ChatClient|ChatModel` 为空），
没有 `api-key`/`dashscope`/`openai` 配置，构建走离线 `mvn -o`。
为一句话引入 Spring AI 意味着：依赖链要联网解析、要新增密钥配置与外呼失败路径、
而部署环境（私有化）未必允许出网。

决策：`RelationSummary` 规则式生成器，只说数据里真有的事（在一起天数 / 打卡天数 / 最长连续 /
补签次数 / 双方都答完的题数 / 已实现愿望数 / 心动值称号 / 最近解锁档位），
**零值整段消失**，不留「答完了 0 道」这种笑话。将来真要接模型，替换点只有这一个方法。

### 8. 双人气泡不加 `private_message` 列

外观由客户端从 `couple.tierUnlocked('bubble')` + 「当前会话对端是不是我的另一半」派生
（ChatView 早已有 `couple.established` 与 `canHeart` 同类先例），
因此「旁人看不到」是结构上成立的——不是同一对会话根本不会带上那个属性，
而不是服务端算好外观再下发。零迁移、零新契约。

### 9. 愿望清单与既有「愿望券本」是两个概念，不合并

`couple_ceremony_coupon`（愿望券）= 花 10 分发出、由对方核销的**承诺凭证**；
`couple_wish`（愿望清单）= 「我想要什么东西」的清单，对方可以偷偷标记已准备。
合并会让"券"的积分语义与"愿望"的惊喜语义互相污染。两个名字各归各的表与端点。

「偷偷」的实现落在领域：`Wish.visibleStatusFor(me)` 把 PREPARED 对许愿人本人回显成 OPEN，
VO 里 `preparedAt` 同步置 null；**标记与撤销一个 WS 事件都不推**（推了就等于替对方说出去）。
这条由 `CoupleWishServiceTest.markingPreparedPushesNothingAtAll`（`verifyNoInteractions(push)`）
与 owner 视角的分组/时刻断言锁住。

### 10. 每日一问不进心动值公式

重建每日一问后，本可以把它加成第七个供数项，但那要重标定七级阈值（0/50/155/…），
而阈值与称号边界是被 `CoupleIntimacyTest` 锁死的产品口径。决策：每日一问不进账，
它的价值由「连续打卡」与彩蛋页时间轴承接。

### 11. 补签定价：20 分 / 7 天窗口 / 每自然月 3 次

用户只说"断签可补签"。自定依据：愿望券 10 分是既有唯一花分出口，补签直接换解锁进度，
定价应高于一张券 → 20 分；只准补最近 7 天（太久以前的日子补回来没有情绪价值，也骗不了自己）；
每自然月 3 次（否则积分充足就等于"不会断签"，连续打卡失去意义）。
花分走 `couple_point_ledger` 的 SPEND，与券本同一账本，余额不足的话术指一条出路（去好事簿记一笔）。

### 12. 不给 `couple_space` 加「一用户一有效空间」的数据库唯一约束

这是本轮**有意没做**的一项，不是遗漏。做法本身成熟（可空 `active_flag` + `UK(user_a, active_flag)`），
但风险不对称：若存量库里已经存在同一用户多行 ACTIVE（正是这个约束要防的病），
V52 会在 Flyway 迁移阶段直接失败，服务**起不来**——在私有化部署环境里，
让一次加列变成可能的停机事件不可接受，而且我没有权限在那里做数据修复。

现状：该不变式继续由 `invite()`/`accept()` 的事前检查兜住（双方各查一次 `findActiveByUser`）。
已知残留风险：两个邀请被**同时**同意时理论上可建出两行 ACTIVE，`partnerOf` 结果会变得不确定。
将来要补的话，正确顺序是"先跑一次重复 ACTIVE 巡检 → 人工确认清行 → 再加约束"，
而不是让约束替数据修复打头阵。

### 13. 定时任务时点

每日一问推送排 09:00（`CoupleQuestionJob`），现存三条是 09:20 生日贺卡、09:30 纪念日倒数、23:00 深夜陪伴，
09:00 是空档；一天跑一次天然按天去重。

## 后果

- 正面：三张新表都靠唯一键兜住不变式（有真库用例证明），外观与解锁态之间没有第二事实源；
  「偷偷」「不没收」「口径只有一条」这三条产品意图都有可失败的红利断言守着。
- 负面：① 只在私聊互动、不点贴贴的日子不算打卡（第 2 条）；
  ② 「一用户一有效空间」仍无数据库兜底（第 12 条）；
  ③ 心动值七级称号与连续打卡档位是两套进度体系，靠"30 天档借用称号显示"这一条桥接，
    读代码的人需要先看本 ADR 才不会以为是重复设计；
  ④ 一句话总结不是真 AI 生成，用户原话里的"AI"要落成真模型仍需另立 ADR 并解决依赖与密钥。
- 服务与时间口径沿用既有现状：定时任务按 `Asia/Shanghai` 触发，服务内取日用 `LocalDate.now()`（系统时区）。
  部署机若非东八区，日界会与推送时点错位——这是裁剪前就存在的既有口径，本轮不动它，
  只在这里记账，避免被误读成新引入的缺陷。
